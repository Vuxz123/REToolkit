# ScriptableObject data contracts

Approved scope: the user approved implementation after the proposal to map types/assets/users, preserve source identity, baseline serialized values and references, compare after recovery, and keep runtime initialization/gameplay separately unverified.

Use the existing Unity validation staging/leases/helper and add opt-in data capture. Capture all stored objects in selected .asset files; ScriptableObject properties include stable GUID/fileID, compiled type/assembly, property paths/types, exact scalar values, array lengths/order, nested fields and object-reference identities. Non-ScriptableObject subassets get identity coverage only. Native recovery and complex field migration retain their existing gates.

Data capture never saves assets or starts Play Mode. Import/OnEnable/deserialization can execute while Unity loads a staged asset; observations describe the loaded state, not original runtime equivalence. Capture all supported properties without the reference scanner's primitive-array skipping. Unknown value kinds, unresolved identity, limits or truncated reports leave data partial. Curve/gradient/exposed-reference/future property kinds initially remain explicit unsupported coverage.

Typed data.capture takes exact .asset IDs and produces a sealed baseline plus canonical validation references under the current asset scope. data.verify takes that baseline and performs fresh staged Unity observation of the same IDs on the current candidate, revalidating build, baseline records, helper, receipts and observation bytes. Compare full object inventories, schema, property values and references; return exact counts with paged differences. Baseline status is never proof the preexisting export matches the original game. Intentional schema/reference migrations must surface differences; no automatic baseline rewrite or guessed normalization.

Expose CLI/MCP/jobs/GUI, bounded data.report pages and readable result sections. Shared recovery artifacts route these operations through the exact candidate; capture/verify are Editor operations and use the existing fork and ownership mechanism. Add workflow dimension data requiring exact assetIds and baselineId; verify only a fresh successful data.verify receipt for the same candidate and scope. Source, data preservation, binding and gameplay remain separate claims. Any later source/data change invalidates the data acceptance observation.

Use source-owned fixtures including arrays, nested fields, references with large numeric fileIDs, hidden subassets, unsupported types, edited observations/baselines, stale builds, schema/value changes, distinct artifacts and mismatched workflow scope. Do not execute user games or a real Unity Editor during this implementation. Live Unity/API behavior remains a separate acceptance check; compile/helper contract checks must not be labeled live gameplay success.
